# Astronomy And Physics Programming Overview

Last updated: 2026-06-04

Purpose: fast big-picture explanation of what DYNAMITE is doing physically and
how that maps onto the code. This assumes the reader understands mathematics
and numerical ODE integration, but not the astronomical workflow.

## One-Sentence Version

DYNAMITE guesses a galaxy mass model, integrates many representative stellar
orbits in that fixed gravitational potential, projects those orbits as an
observer would see them, builds a large matrix saying how much each orbit
contributes to each observed data bin, and solves a non-negative least-squares
problem for orbit weights that best reproduce the observed galaxy.

## What Is An Orbit Here?

An orbit is a representative stellar trajectory in a fixed gravitational
potential.

It is not usually "the measured path of one real star." For an external galaxy
we do not observe individual stellar paths. Instead, each orbit is a basis
function for possible stellar motion inside the assumed galaxy potential.

Numerically, one orbit is generated by integrating the phase-space ODE:

```text
state y = (x, y, z, vx, vy, vz)

d/dt position = velocity
d/dt velocity = -grad Phi(x, y, z)
```

`Phi` is the gravitational potential for one assumed model of the galaxy.

In the active code, the expensive integration is in Fortran:

```text
orblib_fortran/source/orbit_library/orbit_integrator.f90
  integrator_integrate(...)
    -> DOP853
    -> derivs(...)
    -> interpolpot.ip_accel(...)
```

## What Is A Model?

A model is one assumed gravitational setup for the galaxy.

Typical model ingredients:

- stellar light distribution from an MGE, a multi-Gaussian expansion of the
  observed galaxy light
- stellar mass-to-light ratio
- black-hole mass
- optional dark-halo parameters
- intrinsic galaxy shape and viewing angles
- orbit-grid settings

For one model, DYNAMITE treats the potential as fixed. It then asks:

```text
Can a non-negative mixture of orbits in this potential reproduce the observed
light and kinematics?
```

If yes, that model is plausible. If no, that model is a poor description of
the galaxy.

## Why Many Models?

The real galaxy potential is not known exactly. DYNAMITE explores many possible
models with different physical parameters.

Programmatically:

```text
Configuration
  -> parameter space
  -> many Model objects
  -> each Model may need an orbit library
  -> each Model gets weights and chi-square
  -> compare models
```

This is why a full run can be huge: the code is not just integrating one orbit
library. It may integrate orbit libraries for many different assumed galaxy
potentials.

## Why Many Orbits Per Model?

A galaxy contains stars moving in many possible ways. One orbit cannot
represent the whole galaxy. The orbit library samples the possible phase-space
structure of the assumed potential.

The code creates many starting conditions, then integrates them. These include
different energies and orbit-shape parameters. The current DYNAMITE language
often separates tube and box orbit families:

- tube orbits: trajectories with a consistent sense of circulation around an
  axis
- box orbits: trajectories that can pass near the center and do not keep one
  simple circulation sense

The active Python backend first asks Fortran for orbit-start tables:

```text
dynamite/orblib_api.py
  -> orblib_api_run_orbitstart_memory
  -> orbit_start_library.f90
  -> begin arrays for tube and box orbits
```

Then it runs the orbit-library generator twice:

```text
tube starts -> file root "orblib"
box starts  -> file root "orblibbox"
```

## The Core Workflow

For one model:

```text
1. Build gravitational potential Phi.
2. Choose many orbit starting points.
3. Integrate each orbit ODE in that fixed Phi.
4. Sample each trajectory at many times.
5. Project sampled 3D points into the observer's sky plane.
6. Apply symmetry projections.
7. Apply PSF smearing.
8. Map projected points into observed apertures/spatial bins.
9. Bin line-of-sight velocities into LOSVD histograms.
10. Store each orbit's contribution to intrinsic and observed bins.
11. Solve for non-negative orbit weights.
12. Compare weighted model observables to real observed data.
```

The big idea is:

```text
orbit integration gives trajectories
trajectories give observable contributions
observable contributions become matrix columns
NNLS chooses non-negative column weights
weights say how much stellar mass sits on each orbit
```

NNLS means non-negative least squares.

## What Observations Are Being Matched?

The galaxy is observed as projected light and kinematics, not as 3D individual
stellar paths.

Important observed-style quantities:

- surface brightness or luminosity constraints
- spatial apertures or Voronoi bins on the sky
- LOSVDs, line-of-sight velocity distributions, per spatial bin
- optionally stellar-population constraints

LOSVD is central here. For each projected spatial bin, it describes how much
stellar light is observed at different line-of-sight velocities.

The orbit library therefore asks, for every orbit:

```text
If this orbit had unit weight, how much light would it contribute to each
sky bin and each line-of-sight velocity bin?
```

That answer is one large set of numbers per orbit.

## Where The Huge Data Comes From

The data grows as a product of several dimensions.

For one model, think roughly:

```text
number of orbit bundles
  x dithering^3 starting trajectories per bundle
  x many time samples per trajectory
  x symmetry projections
  x PSF samples
  x aperture/bin lookup
  x velocity-bin histogram updates
```

The code does not keep every raw trajectory sample forever. That would be too
large. Instead, Fortran streams samples into accumulators:

- qgrid accumulators for intrinsic 3D information
- LOSVD histogram accumulators for projected observable information
- optional population-mass accumulators
- orbit-class text output

The large persisted data is mainly the orbit-library output matrix-like data:

```text
for each orbit:
  contribution to each intrinsic qgrid cell
  contribution to each observed spatial bin
  contribution to each line-of-sight velocity bin
```

The LOSVD part has the rough shape:

```text
n_orbits x n_velocity_bins x n_spatial_bins
```

That is why memory and disk can become large. If any dimension doubles, the
stored observable contribution data can double. If two dimensions double, it
can grow by about four.

## The Two Big Data Products

### Intrinsic QGrid

The qgrid is the internal 3D view of where an orbit spends time and what
intrinsic moments it contributes.

Programming location:

```text
orbit_library/intrinsic_qgrid.f90
  quadrantgrid.qgrid_store(...)
  quadrantgrid.qgrid_write(...)
```

Python reads it through:

```text
dynamite/orblib.py
```

This is important for intrinsic masses, moments, and orbit properties.

### Projected LOSVD Histograms

The LOSVD histogram is the observer-facing view. It says how much each orbit
contributes to each sky bin and line-of-sight velocity bin.

Programming location:

```text
orbit_library/losvd_histograms.f90
  projection
  psf
  aperture_boxed
  binning
  histograms.histogram_store(...)
```

Python reads it through:

```text
LegacyOrbitLibrary.read_losvd_histograms()
```

The NNLS solver uses this kind of orbit contribution data to fit the observed
kinematics.

## What The NNLS Solve Means Physically

After the orbit library exists, the question changes.

The expensive Fortran part answered:

```text
What would each possible orbit contribute if it had unit weight?
```

The Python NNLS part asks:

```text
Which non-negative weights on these orbits best reproduce the observed galaxy?
```

Mathematically this is a constrained linear problem after the orbit library is
built:

```text
A w ~= b
w >= 0
```

Interpretation:

- `A`: orbit contribution matrix
- `w`: stellar mass/light weight on each orbit
- `b`: observed galaxy constraints

The weights are the reconstructed dynamical structure for that assumed model.

## Why Runs Can Take Weeks

The slow part is usually not Python startup. The expensive work is repeated
numeric accumulation over large orbit libraries and many models.

Main cost drivers:

- number of galaxy models explored
- number of orbit bundles per model
- `dithering^3`
- integration time and ODE tolerance
- number of trajectory samples
- number of symmetry projections
- PSF sampling
- number of spatial bins/apertures
- number of LOSVD velocity bins
- qgrid dimensions
- repeated weight solves over many mass-to-light values or model variants

One model can already be expensive. A full parameter-space search multiplies
that cost by many models.

## Mental Picture

Think of DYNAMITE as building a custom basis for each assumed galaxy potential.

```text
model parameters
  -> gravitational potential
  -> many representative stellar orbits
  -> projected observable fingerprints for each orbit
  -> non-negative mixture of orbit fingerprints
  -> predicted galaxy observables
  -> chi-square against real data
```

The orbits are not the final answer by themselves. They are the basis
functions. The fitted weights on those orbits are the answer for one assumed
model. Comparing many models tells us which physical galaxy parameters are
preferred by the data.
